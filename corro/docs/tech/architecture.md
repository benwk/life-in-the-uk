# 技术架构概览

> 这是一份方向性的概览，目的是让设计和产品的讨论有技术上的依据。详细设计在开始写代码前再补充。

## 整体结构：数据面去中心化，控制面集中

```
                 ┌──────────────── 协调者 Coordinator（Corro 运营）────────────────┐
                 │  调度器        共识引擎        事故引擎        通知器           │
                 │  任务分配      判定 Suspect/   开启、合并、     电话 · 短信 ·     │
                 │  （随机、分散） Corroborated   恢复事故         邮件 · Slack …   │
                 │                                                                 │
                 │  额度账本      信誉系统        透明日志 ──► 每小时锚定到公链      │
                 └──────▲───────────────▲───────────────▲──────────────────────────┘
                        │ 出站 HTTPS（mTLS），节点拉取任务、上报签名见证
          ┌─────────────┴───┐   ┌───────┴─────────┐   ┌─┴──────────────────┐
          │ 社区节点         │   │ 基线节点          │   │ 私有节点             │
          │ 任何人运行        │   │ 多云 serverless   │   │ 客户内网 / Azure     │
          └─────────────────┘   └─────────────────┘   └────────────────────┘

  状态页：静态生成 → 多区域 CDN（和协调者、客户基础设施都独立）
```

为什么控制面不去中心化：告警判定、值班和电话投递需要强一致和高可靠，完全 P2P（DHT、gossip）会让复杂度暴涨，却不会给用户带来更多价值。以后可以学 Matrix 或 Mastodon，做成联邦式，允许别人运行自己的协调者。

## 组件

| 组件 | 职责 | 关键点 |
|---|---|---|
| **节点 Node** | 拉取任务、执行检查、签名上报 | 单个 Go 二进制文件；只需要出站连接；ed25519 身份；资源占用可以设上限；开源 |
| **调度器 Scheduler** | 给每个检查周期挑节点 | 随机、按地区和 ASN 分散；节点不能自选目标；全网频率上限 |
| **共识引擎 Consensus** | 根据见证判定状态 | 规则见 [04 监控与共识](../product/04-monitoring-and-consensus.md)；同一运营者只算一个独立来源 |
| **事故引擎 Incidents** | 开启、合并、恢复事故 | 外部告警源也进入这里 |
| **通知器 Notifier** | 按升级策略发通知 | 电话和短信供应商要有备份；重试；防刷 |
| **信誉系统 Reputation** | 计算节点信誉分 | 金丝雀目标、一致率、在线稳定性 |
| **额度账本 Credits** | 记账 | 每笔变动写进透明日志；不能转让 |
| **透明日志 Transparency log** | 只能追加的 Merkle 日志 | 可以参考 Trillian / Tessera（Go）的实现；存储可以用 Postgres |
| **锚定任务 Anchoring** | 每小时把树头哈希锚定到公链 | OpenTimestamps（比特币）或以太坊 L2 |
| **状态页 Status pages** | 静态生成和分发 | 事件驱动地重新生成；多区域 CDN；首屏不依赖 JavaScript |
| **心跳接收器 Heartbeat** | 接收定时任务的心跳 | 直接在协调者上，不需要节点 |
| **验证工具 `corro verify`** | 离线验证 Receipt | 开源；只依赖公链数据 |

## 数据流：一次检查

1. 调度器为监控选出 3 个节点，生成任务。
2. 节点通过长连接或轮询拉取任务，执行检查。
3. 节点把结果签名后上报：`{node_id, target_hash, ts, result, status_code, latency_ms, sig}`。
4. 共识引擎汇总：全部正常 → Up；有失败 → Suspect，并让调度器追加检查。
5. 满足确认条件 → Corroborated Down → 事故引擎 → 通知器。
6. 见证摘要和判定写进透明日志；额度账本记录节点挣到的额度。

## 可以复用的已有技术（zonic 仓库）

`benwk/zonic` 的技术栈适合作为协调者的基础：

| zonic 已有的 | 在 Corro 里的用途 |
|---|---|
| Go 1.25、Gin、gRPC 双模式（单体 / 微服务） | 协调者先用单体模式部署，以后按需拆分 |
| Identity 服务（OIDC、passkey、workspace） | 多租户账号、团队、SSO；也可以给节点签发身份 |
| PostgreSQL + golang-migrate | 主数据库；透明日志的存储 |
| `pgnotify`（LISTEN/NOTIFY） | 跨副本的缓存失效、状态变化广播 |
| UNLOGGED 表 | 检查结果的短期缓冲、去抖状态、频率计数 |
| OpenTelemetry、Sentry | 协调者自身的可观测性 |

## 需要早期验证的技术风险

| 风险 | 验证方式 |
|---|---|
| 共识延迟：从第一次失败到确认能否 ≤ 60 秒 | 原型：基线节点 + 追加检查，测量端到端延迟 |
| 节点规模：上万节点长连接的协调者负载 | 压测；必要时引入专门的连接网关 |
| 透明日志写入量：每秒数千条见证 | 批量写入（每批组成一棵子树），只写摘要 |
| 电话和短信的到达率 | 至少两家供应商，自动切换 |
| 私有节点的部署体验 | 先做 Docker 和 Azure Container Apps 的一键部署模板 |
