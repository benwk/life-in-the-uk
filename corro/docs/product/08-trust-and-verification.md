# 08 · 可信与验证

## 先说清楚：我们解决的是哪种信任

| 问题 | 靠什么解决 |
|---|---|
| **节点会不会撒谎？**（数据是不是真的） | 多节点共识、信誉、金丝雀检查，见 [04](04-monitoring-and-consensus.md) 和 [07](07-network-and-credits.md) |
| **Corro 会不会改记录？**（数据有没有被改过） | 签名、透明日志、公链锚定，也就是本文 |

区块链类的技术只能保证“写进去之后改不了”，不能保证“写进去的是真的”。所以这两件事要分开设计。

## 用户能得到什么

1. **不可篡改的历史**：状态页上的可用率和事故记录，事后不能被悄悄修改，包括 Corro 自己。
2. **可验证的 SLA 报告**：每个月一份报告，附带证据。客户可以拿给自己的客户或审计员，对方不需要信任 Corro 也能验证。
3. **可审计的额度账本**：节点运营者可以验证自己挣的额度有没有被少算。
4. **中立的证据**：发生 SLA 纠纷时，双方都可以引用同一份公开、可验证的记录。

## 怎么做到

```
节点给每个见证签名 ──► 协调者做共识判定 ──► 写进透明日志（只能追加）
                                               │ 每小时
                                               ▼
                                 把日志的根哈希锚定到公链
                                               │
              任何人都能验证：某条记录确实在日志里、日志从没被改写过、记录的时间
```

### 1. 签名的见证

- 每个节点安装时生成自己的密钥对（ed25519），公钥登记在网络中。
- 每个见证包含：节点 ID、目标（哈希化）、检查时间、结果、状态码、响应时间，并由节点签名。
- 协调者的判定结果（比如“Corroborated Down”）也要签名，并引用它依据的那些见证。

### 2. 透明日志

- 采用证书透明度（Certificate Transparency）和 Sigstore 使用的技术：基于 Merkle 树、**只能追加**的日志。
- 定期发布**签名的树头**（tree head）。任何人都可以：
  - 验证某条记录确实在日志里（包含证明）；
  - 验证新的日志是旧日志的延续，没有删改（一致性证明）。
- 写进日志的内容：见证的摘要、共识判定、事故的开始和结束、状态页的手动调整、额度的增减。

### 3. 公链锚定

- 每小时把最新树头的哈希写到公链上，作为一个外部的时间证明。
- 方案：**OpenTimestamps**（锚定到比特币，免费），或者以太坊 L2（每次成本很低）。
- 我们只是公链的使用者，**不发行任何代币**。链上只有哈希，没有任何目标网址或者客户数据。

### 4. 隐私

- 日志里的目标网址做了加盐哈希处理。外人看不到你在监控什么，你自己（持有盐值）可以证明。
- 私有节点的检查结果也可以写进日志，同样只写哈希摘要。
- 客户可以选择某个监控“不写入公开日志”，代价是这个监控不能显示 Verified 徽章。

## Receipt（凭证）

Receipt 是面向用户的概念，用户不需要懂 Merkle 树。

| Receipt 类型 | 证明什么 | 在哪里出现 |
|---|---|---|
| **事故 Receipt** | 这次故障在什么时间被哪些节点确认，什么时候恢复 | 事故详情页 |
| **每日 Receipt** | 这个组件某一天的可用率计算依据 | 状态页的可用率条 |
| **月度 SLA 报告** | 这个月的整体可用率，附带全部事故的 Receipt | 控制台，可以导出 PDF |
| **额度 Receipt** | 节点在某段时间挣到的额度 | 节点页面 |

### Receipt 的展示

Receipt 在视觉上像一张**打印出来的小票**，见 [设计简报](../design/design-brief.md)：

```
┌──────────────────────────────┐
│  CORRO · INCIDENT RECEIPT    │
│  ──────────────────────────  │
│  api.acme.com                │
│  ▲ Down   09:41:12 UTC       │
│  ● Up     10:04:44 UTC       │
│  Duration 23m 33s            │
│  Witnesses 23 · 5 countries  │
│  ──────────────────────────  │
│  Log #88412907–#88412929     │
│  Anchored 10:00 UTC · BTC    │
│  sha256 9f2c…e41a            │
│  ──────────────────────────  │
│  ✓ Verify  ·  ⤓ Download     │
└──────────────────────────────┘
```

### 验证方式

1. **在线验证**：在 corro.network 上粘贴 Receipt ID，或者扫描二维码，页面会一步步显示验证过程（签名 ✓、日志包含 ✓、锚定 ✓）。
2. **命令行验证**：

   ```bash
   corro verify receipt.json
   ```

   验证工具开源，完全离线运行，只需要公链数据。
3. **证据包**：下载一个 zip，里面有全部签名见证、包含证明和锚定证明，可以交给审计员。

## 在营销中怎么说

- 说 **“可验证”（verifiable）**、**“不可篡改的记录”**、**“独立验证”**。
- 不说“区块链驱动”、“Web3”、“上链”。用户买的是可信，不是技术名词。
- 在技术文档和方法论页面里，再完整说明透明日志和锚定的原理。

## 合规提示

- 额度不能转让、不能提现，这一点在条款中写明，避免被认定为代币。
- 如果面向中国大陆用户提供服务，涉及区块链信息服务的部分可能需要备案，上线前确认。
- 透明日志中不含个人数据；节点运营者的公钥和昵称属于运营者自愿公开的信息。
