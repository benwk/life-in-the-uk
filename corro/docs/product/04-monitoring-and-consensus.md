# 04 · 监控与共识

## 监控类型

| 类型 | 检查什么 | 在哪里运行 | MVP |
|---|---|---|---|
| **HTTP(S)** | 状态码、响应时间、关键字是否出现、响应头 | 社区、基线、私有节点 | ✅ |
| **TCP 端口** | 端口能否建立连接 | 社区、基线、私有节点 | ✅ |
| **DNS** | 记录是否存在、是否等于期望值 | 社区、基线、私有节点 | ✅ |
| **SSL 证书** | 剩余有效天数、证书链是否完整 | 社区、基线、私有节点 | ✅ |
| **心跳 Heartbeat** | 你的定时任务定期请求一个 URL；超时没来就告警 | 协调者（不需要节点） | ✅ |
| **Ping (ICMP)** | 主机能否 ping 通 | 需要权限的节点 | v0.2 |
| **域名到期** | 域名注册剩余天数 | 协调者 | v0.2 |
| **带凭证的检查** | 带 Header 或 Token 的 API 检查、多步骤检查 | **只能在私有节点上运行** | v0.3 |
| **浏览器检查** | 用无头浏览器走一遍关键流程 | 私有节点或基线节点 | 以后 |

**检查间隔**：30 秒、1 分钟、3 分钟、5 分钟。间隔越短，消耗的额度越多。

**新建监控时只需要填一个网址**，其余都有合理的默认值：HTTP 状态码 2xx/3xx 视为正常，超时 10 秒，每次 3 个节点，1 分钟一次。高级设置折叠起来。

## 多节点确认（共识）

这是 Corro 的核心。规则要简单、公开、可解释。

### 默认规则

1. **常规检查**：每个检查周期，从这个监控的节点圈里随机选 **3 个节点**执行检查。
2. **发现异常**：只要有 1 个节点报告失败，状态就变成 **Suspect（疑似）**，并立即调度 **追加检查**：再从不同的地区和 ASN 选 2–4 个节点复查。
3. **确认故障**：满足以下所有条件时，判定为 **Corroborated Down（已确认宕机）**：
   - 失败的见证 ≥ 3 个；
   - 这些见证来自 ≥ 2 个不同的运营者、≥ 2 个不同的 ASN、≥ 2 个不同的国家；
   - 失败的见证占本轮全部见证的比例 ≥ 60%；
   - 失败的节点信誉分都在门槛之上（见 [07 节点网络与额度](07-network-and-credits.md)）。
4. **否决**：追加检查大部分正常时，回到 Up，并在时间线里记录“疑似已否决”。**不发任何通知。**
5. **恢复**：同样需要多方确认，连续 2 个周期多数节点正常，才算 **Corroborated Up**。这是为了避免来回抖动。

用户可以在高级设置里调整：最少见证数（3–7）、地区要求、确认比例。界面上要用一句人话解释当前规则，例如：“至少 3 个节点，来自至少 2 个国家，一致认为无法访问时才告警。”

### 区域性故障

如果失败的见证都集中在某个地区，比如只有亚洲的节点看不到，而欧洲和美洲正常：

- 状态为 **Degraded · Regional（区域性降级）**，并标出受影响的地区。
- 默认通知级别比全局宕机低一级，比如只发 Slack，不打电话。可以在升级策略里调整。
- 这是集中式监控很难给出的信息，要在界面上重点展示：地图上受影响的区域变色。

### 见证不足

节点太少、无法满足确认条件时（比如私有节点池只有 1 个节点），状态为 **Unknown（无法确认）**，并提示用户补充节点。不能假装确认过。

## 状态体系

每个状态都必须同时有**颜色、形状和文字**，色盲用户也能区分。

| 状态 | 形状 | 颜色方向 | 含义 | 会通知吗 |
|---|---|---|---|---|
| **Up** | ● 实心圆 | 绿 | 多方确认正常 | 不会 |
| **Suspect** | ◐ 半圆 | 琥珀 | 有节点报告异常，正在复查 | 不会 |
| **Down** | ▲ 三角 | 红 | 多方确认宕机 | 会，按升级策略 |
| **Degraded** | ◆ 菱形 | 橙 | 变慢、部分失败或区域性故障 | 按设置 |
| **Maintenance** | ◇ 空心菱形 | 紫 | 计划内维护，期间不告警 | 不会 |
| **Paused** | ‖ 暂停符 | 灰 | 用户暂停了监控 | 不会 |
| **Unknown** | ○ 空心圆 | 灰 | 见证不足，无法确认 | 提示补充节点 |

**红色只用于 Down。** 设计中任何其他地方都不要使用这个红色。

## 一次故障的一生

这是最能体现 Corro 差异的场景，事故详情页的时间线要能完整讲出这个故事：

```
09:41:07  东京节点：连接超时（10s）                         ◐ Suspect
09:41:08  调度追加检查：法兰克福、圣保罗、纽约、悉尼
09:41:12  法兰克福：HTTP 503 · 圣保罗：HTTP 503 · 纽约：HTTP 503 · 悉尼：正常
09:41:12  4/5 失败，来自 4 个国家、4 个 ASN、4 个运营者     ▲ Corroborated Down
09:41:13  开启事故 #142；按“生产环境”升级策略通知
09:41:13  推送 → Tom（第一级值班）
09:46:13  5 分钟无人确认 → 电话 Tom
09:47:02  Tom 通过电话按键确认（Ack）
09:49:30  Tom 在状态页发布更新：“正在调查 API 错误”
10:03:44  5/5 节点正常（第 1 个周期）
10:04:44  5/5 节点正常（第 2 个周期）                       ● Corroborated Up
10:04:45  事故 #142 已恢复，持续 23 分 33 秒；状态页自动更新
10:04:45  Receipt 已生成：23 条签名见证 · 日志条目 #88412907 至 #88412929
```

事故详情页要包含：

- **见证地图**：每个节点在地图上的位置和结果，正常和失败用不同的形状标记。
- **时间线**：上面这种逐条记录，包括被否决的疑似。
- **原始证据**：每个见证的状态码、响应时间、错误信息、节点 ID（可以展开查看）。
- **Receipt**：一键验证，或者下载证据包，见 [08 可信与验证](08-trust-and-verification.md)。

## 监控详情页

| 区块 | 内容 |
|---|---|
| 头部 | 名字、目标、当前状态（形状 + 颜色 + 文字）、已持续时间、暂停和编辑按钮 |
| 节点圈 | 当前看着这个监控的节点，排成一个圆环；最近一次检查的结果 |
| 响应时间 | 按地区分组的折线图，默认 24 小时，可以切换到 7 天或 30 天 |
| 可用率 | 90 天的条形图，每天一条；点开一天能看到当天的事故和 Receipt |
| 最近事件 | 最近的疑似、否决、事故 |
| 设置 | 检查间隔、确认规则、关联的升级策略、关联的状态页组件 |

## 外部告警源

为了替代 Opsgenie，Corro 也要能接收**别人产生的告警**，这类告警不经过节点确认，直接走升级策略：

- Prometheus Alertmanager、Grafana、Datadog、AWS CloudWatch、Azure Monitor、通用 Webhook、邮件转告警。
- 这些告警在界面上标注来源，并明确标注“未经 Corro 节点确认”。
- 同一个服务的多条告警自动合并成一个事故，避免一次故障响十次。
